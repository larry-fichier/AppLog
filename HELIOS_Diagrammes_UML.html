Diagramme 03 — Séquence

Connexion et mot de passe obligatoire

Quand un admin a coché « mot de passe par défaut » lors d'une réinitialisation, l'utilisateur reste bloqué derrière un écran de changement de mot de passe jusqu'à en définir un nouveau — l'état est porté par le serveur (must_change_password), pas seulement par l'écran de connexion. 

sequenceDiagram
    actor U as Utilisateur
    participant F as Frontend
    participant API as API /api/auth
    participant DB as PostgreSQL

    U->>F: Identifiant + mot de passe
    F->>API: POST /api/auth/login
    API->>DB: SELECT * FROM users WHERE username = ?
    DB-->>API: Utilisateur + password_hash
    API->>API: bcrypt.compare(password, hash)
    alt Identifiants invalides
      API-->>F: 401 Identifiants invalides
      F-->>U: Message d'erreur
    else Identifiants valides
      API->>API: Génère un JWT (jti unique)
      API-->>F: 200 { user, mustChangePassword }
      F->>F: sessionStorage.setItem("helios_user", …)
      alt mustChangePassword = true
        F-->>U: Écran « Mot de passe à changer » (bloquant)
        U->>F: Ancien + nouveau mot de passe
        F->>API: POST /api/auth/change-password
        API->>DB: UPDATE users SET password_hash,
must_change_password = false
        DB-->>API: OK
        API-->>F: 200 succès
        F-->>U: Accès normal à l'application
      else mustChangePassword = false
        F-->>U: Accès normal à l'application
      end
    end
Diagramme 04 — Séquence

Demande et approbation d'un transfert

Un COM Zone ne peut pas déplacer un équipement librement : son mouvement de type transfert part en attente et doit être validé par le Chef de Bureau ou la CSA avant que la zone de l'équipement ne change réellement. 

sequenceDiagram
    actor CZ as COM Zone
    participant F as Frontend
    participant API as API /api/movements
    participant DB as PostgreSQL
    actor CB as Chef de Bureau / CSA

    CZ->>F: Sélectionne équipement + zone destination
    F->>API: POST /api/movements (type = transfert)
    API->>DB: INSERT movements (status = pending)
    API-->>F: 201 Créé
    API--)CB: SSE movement_transfer_requested
    Note over CB: Notification temps réel (cloche)
    CB->>F: Ouvre l'onglet Mouvements
    F->>API: GET /api/movements?status=pending
    API->>DB: SELECT … WHERE status = pending
    DB-->>API: Transferts en attente
    API-->>F: 200
    CB->>F: Approuve ou rejette (motif obligatoire si rejet)
    F->>API: POST /:id/approve ou /:id/reject
    API->>DB: UPDATE movements SET status, decision_note
    API->>DB: UPDATE equipment SET zone_id (si approuvé)
    API--)CZ: SSE movement_transfer_approved | rejected
    Note over CZ: Notification temps réel, motif si rejeté
Diagramme 05 — Séquence

Déclaration d'un écart de stock

Une déclaration qui confirme le stock existant s'applique immédiatement ; un écart crée une stock_declaration en attente, arbitrée par le Chef de Bureau ou la CSA avant de toucher le stock réel de la zone. 

sequenceDiagram
    actor CZ as COM Zone
    participant API as API /api/equipment/:id/declare-stock
    participant DB as PostgreSQL
    actor CB as Chef de Bureau / CSA

    CZ->>API: POST { quantité déclarée }
    API->>DB: Lit quantite_stock actuelle
    alt Quantité = stock actuel
      API->>DB: INSERT movements (ajustement, aucun écart)
      API-->>CZ: 200 Déclaration confirmée
    else Écart détecté
      API->>DB: INSERT stock_declarations (status = pending)
      API--)CB: SSE stock_declaration_created
      Note over CB: Notification temps réel
      CB->>API: POST /approve ou /reject (motif obligatoire si rejet)
      alt Approuvé
        API->>DB: UPDATE equipment_details SET quantite_stock
        API->>DB: UPDATE stock_declarations SET status = approved
        API--)CZ: SSE stock_declaration_approved
      else Rejeté
        API->>DB: UPDATE stock_declarations SET status = rejected,
decision_note
        API--)CZ: SSE stock_declaration_rejected (avec motif)
      end
    end
Diagramme 06 — Séquence

Sortie de stock central vers une zone

Quand le Chef de Bureau envoie du stock central vers une zone, l'instance de stock de cette zone est créée si besoin et le ravitaillement est enregistré déjà « fulfilled » — le COM Zone n'a plus qu'à confirmer réception à l'arrivée du matériel. 

sequenceDiagram
    actor CB as Chef de Bureau
    participant API as API /api/equipment/:id/stock-sortie
    participant DB as PostgreSQL
    actor CZ as COM Zone (destination)

    CB->>API: POST { quantité, zone destination }
    API->>DB: Décrémente quantite_stock (article central)
    API->>DB: INSERT movements (type = sortie)
    API->>DB: Cherche / crée l'instance d'équipement de la zone
    API->>DB: INSERT resupply_requests (status = fulfilled)
    API--)CZ: SSE resupply_fulfilled
    Note over CZ: Apparaît dans l'onglet Ravitaillements
    CZ->>API: POST /:id/confirm { quantité reçue }
    API->>DB: UPDATE equipment_details SET quantite_stock
+= quantité reçue (zone)
    API->>DB: UPDATE resupply_requests SET status = confirmed
    API->>DB: INSERT movements (type = entree, zone)
    API--)CB: SSE resupply_confirmed
Diagramme 07 — Séquence

Déclaration de panne et notification

La panne est diffusée en direct par SSE à tous les rôles concernés sauf son auteur ; un rôle non connecté au moment de l'envoi la retrouve à sa prochaine connexion via un rejeu construit depuis le journal d'audit, pas seulement depuis le flux temps réel. 

sequenceDiagram
    actor CZ as COM Zone / Chef RAM
    participant API as API /api/equipment/:id/panne
    participant DB as PostgreSQL
    participant SSE as Diffusion SSE
    actor Dest as Chef Bureau / Chef RAM / CSA / CSPH / Admin

    CZ->>API: POST { description obligatoire }
    API->>DB: UPDATE equipment SET status = en_reparation
    API->>DB: INSERT movements (ajustement)
    API->>DB: INSERT audit_logs (EQUIPMENT_PANNE_DECLAREE)
    API->>SSE: broadcastEvent(equipment_critical, excludeUserId)
    SSE--)Dest: Notification temps réel (sauf l'auteur)
    Note over Dest: Cliquable → détail complet
    opt Destinataire non connecté à l'envoi
      Dest->>API: GET /api/notifications/recent (à la connexion)
      API->>DB: SELECT … FROM audit_logs
WHERE action = EQUIPMENT_PANNE_DECLAREE
      DB-->>API: Historique récent
      API-->>Dest: Notifications reconstituées
    end
Diagramme 08 — Séquence

Réforme d'un véhicule

Réservée au Chef RAM et à l'Admin : le véhicule sort définitivement du parc actif (soft-delete), mais son historique de mouvements reste consultable — la traçabilité survit à la sortie du parc. 

sequenceDiagram
    actor CR as Chef RAM
    participant API as API /api/equipment/:id/reformer
    participant DB as PostgreSQL

    CR->>API: POST { destinataire obligatoire, note }
    API->>DB: UPDATE equipment SET status = reforme,
deleted_at = NOW()
    API->>DB: INSERT movements (traçabilité conservée)
    API->>DB: INSERT audit_logs (EQUIPMENT_REFORME)
    API-->>CR: 200 succès
    Note over API,DB: Historique consultable ensuite via
GET /api/equipment/:id/history
(ignore deleted_at)
